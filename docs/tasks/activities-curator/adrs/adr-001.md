# ADR-001: The curator edits the document; code applies the edits and enforces one rule

## Status

Accepted (user direction, 2026-10-19; amended in review round 3: the document-level backstop was removed, by the user's decision)

## Date

2026-10-19

## Context

The user needs one place with everything still open from any meeting. Several shapes were considered in the 2026-10-19 conversation. The user rejected a deterministic task store as over-engineered for the pain and said deterministic code would make the result worse; judgment must live in an agent. An agent that keeps a long Markdown document, though, is weak at copying thousands of tokens verbatim: a whole-document rewrite drifts (rewording, reordering, dropped sub-lines) and costs output proportional to the document.

## Decision

After each analyzed meeting (or batch of up to four), a curator agent returns edit operations shaped like an editor's Edit tool: `replace`, `insert_after`, `move`, `archive`, each targeting whole lines of the current document (`move` adds an anchor line: code cuts the target and pastes it after the anchor byte for byte). Code re-reads the file under a lock, applies the operations in order, and enforces exactly one rule, in one sentence: only `archive` takes a checkbox line away, and no edit changes a box. The rule is checked per edit (a `replace` keeps at least its target's open lines and exactly its ticked lines; an `insert_after` adds no ticked line; a `move` cannot change a count). Lines no edit targets are preserved byte for byte by the applier itself, so there is no second, whole-document check. The rule guards checkbox state and count, not line identity: keeping a replaced line's wording is a prompt rule measured by the evaluation. Everything else — what is new, what matches what, where it goes, what leaves, the focus — is the agent's, stated in its prompt. One retry with only the failed operations; otherwise nothing is written. Code also writes the box from the agent's `focus` and regenerates link definitions from the labels in use; it never parses item lines.

## Alternatives Considered

### Alternative 1: Deterministic task store

- **Description**: a `Task` aggregate with ids, ingestion markers, matching rules, code-computed overdue and ranking; Markdown rendered from it.
- **Pros**: exact, testable, no model drift.
- **Cons**: matching by text is wrong in Portuguese (e.g. "enviar relatório" vs "revisar relatório" scored 0.95 similarity); many special cases (ids across re-analysis, reingest, markers); the user perceives a system, not a document.
- **Why rejected**: the user rejected it explicitly.

### Alternative 2: Whole-document rewrite by the agent

- **Description**: the agent returns the full new document.
- **Pros**: simplest contract; the agent has total freedom.
- **Cons**: drift on untouched items, output grows with the document (truncation risk), user edits depend on faithful copying, detecting a lost item needs a line-by-line validator.
- **Why rejected**: copying is not judgment; it fails at exactly what the user cares about (nothing disappears, edits stand).

### Alternative 3: A document-level count of open lines

- **Description**: the first draft's rule, `open(result) + open(archived) ≥ open(before)`, or its line-by-line variant (every open line of the old document must reappear unchanged).
- **Pros**: one check, no per-edit logic.
- **Cons**: the count form is blind to drop-B-add-C and tick-A-add-C, which is nearly every pass because passes add items; the line form rejects the edits the prompt requires on open lines (date change, mention link, 💤), so legitimate passes are discarded.
- **Why rejected**: the review of round 1 (issue 001) showed neither form can be implemented to do what the rest of the spec requires; the per-edit form catches the failure where it happens and gives the repair step a reason.

### Alternative 4: Edit operations with numbered anchors and code guards (design v1)

- **Description**: blocks numbered per pass; code converts or refuses ops by rules (identity with last version, duplicate_of, section ownership), optimistic redo when the file changes.
- **Pros**: strong protection.
- **Cons**: code overrules the agent in six places; anchors break when the user edits during the call; reintroduces the rejected machinery.
- **Why rejected**: critic round 1 (blocking finding).

### Alternative 5: A whole-document backstop (`check_open_invariant`)

- **Description**: after the ops apply, check that every open line no `replace`/`archive` targeted is still in the result byte for byte, and discard the pass otherwise (rounds 1 and 2).
- **Pros**: a second line of defence against an applier bug.
- **Cons**: it re-checks what `apply_ops` already guarantees by construction (untouched lines are copied byte for byte); its only possible failure was, by the spec's own wording, an implementation defect, which tests of `apply_ops` catch where it is written; it added a function, an error row, a test table and an exemption list (`Applied.targets`) to maintain.
- **Why rejected**: the user chose to remove it (review round 3): the per-op rule and the applier's byte-for-byte preservation already deliver the user-facing guarantee, which is unchanged: only `archive` takes a checkbox line away, and only the user changes a box.

## Consequences

### Positive

- Untouched text is byte-identical, including the lines a move passes; the user can edit during a pass.
- Small outputs; no drift on unchanged items.
- The agent decides every change; the user experiences "an agent that keeps my document".

### Negative

- The agent must copy target lines exactly; retries happen.
- The agent must still copy each `replace` text faithfully; code checks state and count, not identity (measured by Q-002). A reorder is a `move`, so a `replace` never has to re-emit lines it does not change. The first round-2 draft used a spanning `replace` for moves and let the model re-copy every line it passed, unchecked; `move` removes that copy.
- Most rules are prompt-level, so quality is measured, not guaranteed.

### Risks

- Retry rate on long lines with emoji or quotes — mitigated by anchoring guidance and logged per op kind.
- Wrong match (duplicate or 💬 on the wrong item), or a `replace` that rewrites a neighbouring line with the same counts — measured by the sequence evaluation and the shadow week; `undo` and versions as the safety net.

## Implementation Notes

`domain/activities.apply_ops` matches targets (and `move` anchors) as whole lines after stripping trailing whitespace, only inside the body, and applies the per-edit checkbox rule; a violation is an `OpFailure("breaks the checkbox rule", detail)` that reaches the repair step like a target mismatch. There is no backstop: `apply_ops` leaves every line no edit targets byte for byte as it was (Safety Invariant 4, UT-001, UT-023, UT-113), and the per-op rule guards what the curator does target.
