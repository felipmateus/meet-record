# ADR-003: A pass commits in a recoverable order; the pass-log line is the commit point

## Status

Accepted (review round 1, issue 007; amended in review round 2, issues 001, 002 and 008; amended in review round 3, issue 002; the user approved fixing all findings)

## Date

2026-10-19

## Context

A pass changes five things that live in separate files: the version files, the archive, the document, `base.md` and the pass log. The first draft listed them in an order that made "a pass writes everything or nothing" false: if the document replace failed after the archive append, the archive and versions were already written, the pass log had no record to truncate by, and the rerun archived the same items twice. A hard stop after the document replace and before `base.md` made the next diff show the whole previous pass as the user's edits, so the curator would freeze its own lines as user-authored.

## Decision

`ActivityStore.commit` first builds the archive entries and measures each archive file's size before and after the append, then writes, in order: the version files (`_before`, `_after`, `_base`, `_prevbase`, `_pass.json` holding both sizes), the archive entries, the document (atomic replace), `base.md`, and last the pass-log line, which is the commit point. The closing marker of the document's box carries a stamp, the pass version (`<!-- curador:fim 20261019-101200 -->`), written by `render_box`. A failure raised inside the process undoes what was done (truncate the archive files to their sizes before and delete the version files before the document replace; retry the remaining steps after it). After a hard stop, `lock()` reconciles on entry each version set that has no pass-log line (a torn last JSONL line counts as absent): the document was replaced iff `box_stamp(document)` is not None and equals `box_stamp(_after)`: a pass writes its version as the stamp, so its `_after` carries it, while an undo renders no box and its `_after` is the restored text, whose stamp is an earlier pass's or, when the first pass is undone, the skeleton's fixed sentinel (`DocFormat.skeleton_stamp`, `00000000-000000`, written in the closing marker of the skeleton), so every `_after` the app produced for a pass carries a stamp (an undo's `_after` is the restored `_before_N` and has none only when the user had removed the marker before pass N, and then reconcile rolls back); a document with no stamp is never counted as replaced. Replaced → roll forward (`base.md` from `_base`, or deleted when the set has no `_base` file; pass-log line from `_pass.json`); otherwise roll back (archive truncated to its size before, files deleted). Undo goes through the same journal: its set holds the current document as `_before`, the restored text as `_after` and the undone pass's `_prevbase` as `_base` (none when the undone pass was the first, because no `base.md` existed then: `base` is `None`, no `_base` file is written and `base.md` is deleted, so the next pass starts with no base and an empty `user_edits`); its `carried_edits` is ""; its pass-log line is written before the archive is truncated, and the truncation, last, happens only while the archive still has the size recorded after the undone pass.

## Alternatives Considered

### Alternative 1: Relax the invariant to "document and base unchanged; the archive may hold entries reconciled later"

- **Description**: keep the order, accept surplus archive entries, reconcile by truncation.
- **Pros**: no recovery code.
- **Cons**: leaves the hard-stop window around `base.md` open; duplicated archive entries on every failed replace until something reconciles them.
- **Why rejected**: it weakens a stated guarantee instead of meeting it.

### Alternative 2: Write `base.md` before the document

- **Description**: the review's suggestion: a stale document with a new base is "harmless because the pass is rerun".
- **Pros**: closes the window after the document.
- **Cons**: a stale document against a new base reads as the user deleting everything the pass added; the next pass would archive those items as `removido por você` or treat them as an editor overwrite.
- **Why rejected**: not harmless; it moves the damage instead of removing it.

### Alternative 3: A write-ahead journal file separate from the versions

- **Description**: `.curator/commit.json` listing the steps.
- **Pros**: explicit.
- **Cons**: a second source of truth next to files the pass already writes.
- **Why rejected**: the version triple and `_pass.json` already hold everything needed, and "no pass-log line" is a sufficient marker.

### Alternative 4: Decide by comparing the document with `_before` (this ADR's first version)

- **Description**: roll back only when the document is byte-identical to `_before`, otherwise roll forward.
- **Pros**: no extra state.
- **Cons**: a stop before the replace followed by a user edit looks exactly like a stop after the replace followed by a user edit; the wrong guess rolls forward a document that was never replaced, writes a `base.md` containing everything the pass added and marks the meetings curated, so the next pass reads the pass's own items as deleted by the user (review round 2, issue 001).
- **Why rejected**: it reproduces the damage Alternative 2 was rejected for.

### Alternative 5: An empty `_replaced` marker file written right after the replace

- **Description**: the review's suggestion: replaced iff the marker exists or the document equals `_after`.
- **Pros**: simple.
- **Cons**: a stop between the replace and the marker, then a user edit, is still ambiguous.
- **Why rejected**: the stamp lives in the document itself, so the replace is observable at every instant with no extra file.

## Consequences

### Positive

- The all-or-nothing invariant holds for raised errors and, after reconciliation, for hard stops.
- A surplus archive entry is the only possible residue, never a missing one.

### Negative

- Five small files per pass instead of two (kept for the last 50 passes), a stamp in the box's closing marker, and reconciliation code with its own tests.

### Risks

- A user who deletes or rewrites the stamp in the box's closing marker between a hard stop and the next lock makes a replaced document look unreplaced, and the roll back truncates archive entries for items already out of the document. Needs a hard stop inside the few-millisecond commit window plus an edit of a marker the file says to leave alone: accepted; the versions keep the lost text. The same rule applies to an undo: a stop after the document restore plus a deleted or rewritten stamp rolls the undo back although the restore reached the file, which leaves the consistent "undo did not happen" state (the pass still counts, `base.md` and the archive are intact) while the document holds the restored text, not the pass's `_after`, so the user retries `undo` before the next pass (a pass run first reports the undone pass's items as deleted by the user in `user_edits`); the other choice, counting a missing stamp as replaced, would roll an unrestored first-pass undo forward and make the pass impossible to undo.
- The roll-back direction also happens after an undo of a pass whose `_before` had no stamp (the user removed the marker before that pass, or the file was not created by the app), with no edit after the stop: the restored text has no stamp, so a stop after the document restore rolls the undo back. Same state and same remedy as above: the document holds the restored text, the pass still counts, and the user re-runs `trec activities undo`.
- An editor overwrite that restores an old buffer also restores an old stamp: for a pass reconciliation rolls back, which matches what is on disk; for an undo whose restored text carries that same older stamp it rolls forward, which also matches what is on disk.
