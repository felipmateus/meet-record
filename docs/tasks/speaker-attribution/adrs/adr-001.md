# ADR-001: Speaking state from the tile frame's class set, read through Accessibility

## Status

Proposed

## Date

2026-10-16

## Context

Teams delivers one mixed audio stream and writes nothing about speakers to its logs, yet its client receives the active-speaker list from the service and renders it. The investigation (`docs/SPEAKER-ATTRIBUTION.md`) compared the local and cloud sources of "who is speaking" and the spike runs established what the macOS Accessibility API exposes of the new Teams client: participant tiles as `AXMenuItem` elements with the display name as text, no textual speaking state, and an empty frame element inside each tile whose DOM class list gains `vdi-frame-occlusion` plus eight atomic classes while the participant speaks (run 8: 12 transitions in 115 s in sync with a colleague's speech bursts). The tree updates only while a Teams window is rendered; the compact view Teams keeps on top when the meeting loses focus updates too.

## Decision

Read the speaking state from the Teams meeting windows through the Accessibility API, polling every 0.5 s: a participant is speaking while the frame element of their tile carries the `vdi-frame-occlusion` class set, in the main window or the compact view. Record events with wall-clock times and the tile's text, so a future change in Teams is diagnosable. The reader is a separate helper (`teams-speakers`) with its own Accessibility permission, read-only on Teams.

## Alternatives Considered

### Alternative 1: Teams' own transcript through Microsoft Graph

- **Description**: fetch the speaker-attributed VTT of the meeting after it ends.
- **Pros**: names per utterance from Microsoft; no UI dependence.
- **Cons**: requires the tenant to allow transcription and Graph access, admin consent for the delegated permission, someone to start transcription in each meeting, which every participant sees; meetings expire.
- **Why rejected**: not under the user's control and changes the footing of the recording from private to announced.

### Alternative 2: Per-meeting voice clustering (diarization without enrolment)

- **Description**: segment and cluster voices locally (sherpa-onnx or FluidAudio), label `SPEAKER_00…N`, name them from context.
- **Pros**: works with any window state; no Teams dependence.
- **Cons**: a neural model with 10–20% error, worse on overlap; more CPU on the development Mac; anonymous labels still need names.
- **Why rejected** for this delivery: the window gives real names at near-zero cost when visible; clustering stays the fallback if coverage (gate G2) proves insufficient.

### Alternative 3: Stereo position with Teams' spatial audio

- **Description**: keep the Teams track stereo and read the pan of each voice.
- **Pros**: zero model; already captured.
- **Cons**: requires spatial audio on, wired or built-in stereo output, gallery view, more than two participants; positions move when the gallery re-sorts; gives positions, not names.
- **Why rejected**: fragile and nameless.

### Alternative 4: Text signals in the accessibility tree (captions pane, announcements)

- **Description**: read the live captions (`Name: text`) or the live-region announcements.
- **Pros**: text, not a class name.
- **Cons**: captions must be switched on by the user per meeting and are not saved; announcements carry mute state only (runs 2, 7).
- **Why rejected**: depends on a per-meeting user action; the frame class needs none.

## Consequences

### Positive

- Real display names, no enrolment, nothing leaves the Mac; the data already exists on screen.
- Resolution of 0.5–1 s, enough for whisper's segments.

### Negative

- Dependence on Teams' DOM: a redesign can silence the labels.
- A fully covered Teams window stops the signal; the user must keep one visible (the compact view usually is).

### Risks

- UI drift: mitigated by recording the tile text with each event, counters in the `stop` event, the labelling summary stored with the transcript (so `trec status` shows `0%` with the reason), the daily notification and the probe script for re-discovery.
- Permission identity: which process macOS holds responsible for the helper is settled by a spike before wiring (spec, task 0); `trec doctor` warns when its own check and the last recording disagree.
- Chromium's accessibility mode costs Teams memory while attached: measured by gate G5; the feature can be switched off.

## Implementation Notes

The helper derives from `scripts/ax-speaker-probe.swift` (window detection, tile text, `AXDOMClassList`, transition logging by element path), minus the probe's `AXEnhancedUserInterface` write: the helper sets no accessibility attribute at all (spec, safety invariant 4). The own tile exposes no frame, hence ADR-002.
